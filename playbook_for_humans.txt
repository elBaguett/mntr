Playbook: CrashLoopBackOff Pod

Цель: выявить причину перехода пода в CrashLoopBackOff и восстановить его работу.

    Определить имя пода и его namespace:
        Выполнить kubectl get pods -A | grep CrashLoopBackOff.
    Снять логи с пода:
        Выполнить kubectl logs <имя-пода> -n <namespace>.
        Если контейнер рестартуется слишком часто, указать параметр --previous для прошлого контейнера.
    Проверить описание пода:
        Выполнить kubectl describe pod <имя-пода> -n <namespace>.
        Изучить раздел Events на наличие ошибок и причины перезапусков (например, ImagePullBackOff, ошибочный entrypoint, отсутствие переменных окружения, ошибки инициализации).
    Проверить статус всех зависимостей (ConfigMap, Secret, PVC) и наличие достаточных ресурсов CPU/Memory, задать resource limits, если поду не хватает памяти.
    В случае ошибок типа невалидного конфига или секрета — исправить ошибку в ресурсе Kubernetes, перезапустить под.
    Если проблема не решается — удалить под: kubectl delete pod <имя-пода> -n <namespace>. Репликация поднимет новый экземпляр.
    Если после исправления проблема не исчезает — эскалировать DevOps/разработчику с логами и всеми изменениями.

Playbook: Node NotReady

Цель: обнаружить причину, по которой Kubernetes-нода перешла в статус NotReady, и восстановить её работоспособность.

    Проверить список нод и их статус:
        Выполнить kubectl get nodes.
    Собрать подробную информацию о NotReady-нОДе:
        Выполнить kubectl describe node <имя-ноды>.
        Изучить секции Conditions и Events, проверить дисковое пространство, наличие swap, статус сетевых интерфейсов.
    Проверить на ноде локально:
        Подключиться через SSH, проверить статус kubelet: systemctl status kubelet.
        В случае падения перезапустить процесс: systemctl restart kubelet.
        Проверить наличие swap: swapon --show. Swap должен быть отключен.
        Проверить свободное место на root-диске: df -h.
    Проверить сетевую связность — пинги до master, доступность API.
    Если требуется, вывести ноду из планирования: kubectl drain <имя-ноды> --ignore-daemonsets --delete-emptydir-data.
    Если проблема вызвана физическим сбоем (EC2 статус Impaired, проблемы с диском) — восстановить instance либо заменить ноду.
    После устранения причины перезапустить kubelet, вернуть ноду в кластер: kubectl uncordon <имя-ноды>.

Playbook: Высокая задержка API Server

Цель: найти причину роста задержек в работе API сервера Kubernetes и минимизировать их.

    Проверить нагрузку на master-ноды:
        Выполнить kubectl get pods -n kube-system, определить загруженные компоненты.
        Проверить ресурсы EC2: CPU, RAM.
    Проверить метрики control-plane (CPU, IO, network latency).
    Изучить логи kube-apiserver для выявления ошибок или блокирующего поведения.
    Проверить количество открытых соединений, очередь запросов, уровень ошибок.
    По возможности временно уменьшить нагрузку (приостановить деплой новых pod’ов).
    Увеличить ресурсы master-нод или добавить дополнительные экземпляры (HA).
    В случае возникновения DDoS атаки или избыточного автоскейлинга — применить задание лимитов и рестартовать сервисы, если требуются.

Playbook: 5xx ошибки на Application Load Balancer

Цель: выявить причину появления 5xx ошибок на ALB и устранить источник ошибок.

    Уточнить имя ALB, по которому срабатывает алерт (см. в alarm или дашборде).
    Перейти в AWS > EC2 > Target Groups, выбрать нужный target group, привязанный к ALB.
    Проверить статус всех таргетов, определить unhealthy backend.
    В кластере найти соответствующий pod или deployment:
        kubectl get pods -n <namespace>
        kubectl describe pod <имя-пода> -n <namespace>
        kubectl logs <имя-пода> -n <namespace>
    Проверить readiness и liveness probes в манифестах deployment, исправить при необходимости.
    Если выходят из строя все pod-ы — проверить конфиги (секции env, secret, image).
    Проверить логи ALB (если подключены access-логи) на уровне балансировщика для детализации причин ошибки.
    После устранения ошибок перезапустить приложения, убедиться в исчезновении 5xx статуса.

Playbook: Frontend 5xx ошибки (через ELB/ContainerInsights)

Цель: определить причину высокого числа 5xx ошибок на frontend сервисе.

    Получить подробную статистику по дашборду (ELB, ContainerInsights).
    Определить, есть ли валидные backend сервисы для frontend:
        Проверить deployment: kubectl get deployment -n frontend
        Проверить состояние pod’ов: kubectl get pods -n frontend
    Проверить конфигурацию ingress (nginx/ALB), убедиться, что маршрутизация работает.
    Снять логи frontend pod и подов backend, которые вызываются через этот frontend.
    Проверить секции с ошибками в логе, при необходимости локально воспроизвести запросы с помощью curl.
    Исправить найденные ошибки (application bug, bad config, отсутствующий secret/env).
    Перекатить deployment с фиксом, проконтролировать изменение метрик на дашборде.

Замечания:

    После устранения каждой из типовых причин обязательно контролировать метрики на дашборде до стабилизации.
    Любое действие, влияющее на доступность сервиса, фиксировать в инцидент/оперативный чат с указанием времени и сожержания исправлений.
